# Project Status Report Skill

## When to use
- A weekly, fortnightly, or monthly project status update is needed for sponsors or steering committee
- A project is off-track and an escalation report is needed to explain the situation and get a decision
- A programme of work needs to be summarised across multiple workstreams
- A project close-out report is needed to document outcomes and lessons learned
- A project budget overrun needs to be formally reported with a revised plan

## Status indicators
Use these standard traffic light ratings consistently:

| Status | Meaning |
|---|---|
| 🟢 Green | On track — no material issues |
| 🟡 Amber | At risk — issues identified, mitigation in progress, escalation may be needed |
| 🔴 Red | Off track — material issues requiring sponsor decision or escalation |

Rate the overall project and each key dimension separately: **Schedule**, **Budget**, **Scope**, **Resources**, **Risks**.

## Report structure

### Standard project status report
1. **Overall status** — traffic light rating and one-sentence summary of where the project stands this period.
2. **Progress this period** — what was completed since the last report? Be specific — list milestones achieved, deliverables completed, decisions made.
3. **Planned for next period** — what is scheduled to be completed before the next report? Include milestone dates.
4. **Schedule status** — are key milestones on track? If amber or red, state which milestones are at risk and by how many days/weeks.
5. **Budget status** — actual spend vs budget to date. Forecast to complete vs original budget. Explain any material variances.
6. **Key risks and issues**
   - Issues (problems that have already occurred): describe, state impact, and state resolution plan with owner and deadline.
   - Risks (potential problems): describe, state likelihood and impact, state current mitigation.
7. **Decisions required** — explicit list of decisions needed from the sponsor or steering committee, with the deadline for each decision and the consequence of delay.
8. **Dependencies** — external dependencies that are at risk of causing delays. Who owns each dependency?

### Project close-out report additions
- Outcomes delivered vs objectives stated at project initiation
- Benefits realised vs benefits case
- Budget final vs approved budget
- Lessons learned (what worked, what should be done differently)
- Handover to BAU: who owns what going forward

## Writing rules for status reports
- Be direct about problems. Amber and red statuses exist to be used — a project that is consistently green but then fails has poor reporting.
- State decisions clearly: "The steering committee needs to decide by [date] whether to [specific choice]. If this decision is not made by [date], [specific consequence] will result."
- Do not use vague status descriptions ("progressing well", "some challenges"). Quantify — "3 of 5 planned milestones completed; 2 are delayed by 2 weeks each."
- Separate issues (happening now) from risks (could happen). They require different responses.
- Every action item must have an owner and a deadline.

## Tone
Factual, precise, and action-oriented. Status reports are read under time pressure — structure them so a sponsor can identify problems and required decisions in 90 seconds.
